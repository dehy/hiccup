# ADR 0001: Shared Rust core with three native frontends

- **Status:** Accepted
- **Date:** 2026-11-26

## Context

Hiccup must run on Linux, macOS and Windows, and the maintainers want a truly native user interface on each OS rather than one cross-platform toolkit (web view, Qt, egui, …).

## Decision

- Put all behaviour in a **UI-agnostic Rust core**: proxying, TLS, storage, repeater, and also parsing, formatting, filtering and diffing.
- Build one **native frontend per OS**:
  - Linux: **GTK4 + libadwaita** through `gtk4-rs`. This links the core directly in Rust, with no FFI.
  - macOS: **SwiftUI**, using bindings generated by **UniFFI**.
  - Windows: **WinUI 3 / C#**, using bindings from `uniffi-bindgen-cs`. The fallback is a C ABI (`cbindgen`) with P/Invoke, chosen by a spike in M3.
- Keep frontends **thin**. They render view-models and forward user intents, and they contain no protocol logic.
- Ship a **CLI** (`hiccup`) with full feature parity. It drives the core through the local control API, including a running GUI instance (see [ADR 0004](0004-cli-control-plane.md)). It is the first consumer of every feature and the base for end-to-end tests.
- Build frontends in this order: **Linux → macOS → Windows**.

## Consequences

- The UI is built three times, in three languages (Rust, Swift, C#). Mitigations: a thin-frontend rule, a shared parity checklist for each milestone, and view-models defined in the core.
- An FFI boundary has to be designed and versioned (M3). It must support async calls and event streams.
- `uniffi-bindgen-cs` is maintained by the community, not by Mozilla. This is a known risk with a documented fallback.
- Contributors can work on one platform's UI without knowing the others.
